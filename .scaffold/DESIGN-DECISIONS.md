| D-009 | Workflows | Scheduled jobs | Overdue check, recurring task generation, stale cleanup, plus four retention sweeps. Cron schedules are declared on `[TickerFunction(name, cron)]`, so TickerQ seeds them idempotently when the host runs, inside the `EF.BackgroundServices.TickerQ` seed lock; each job runs its handler through `ScheduledJobRunner`; `AddSchedulerHealthCheck<TaskFlowTickerQDbContext>` reports Degraded when no job has run within `Scheduling:Health:StallThreshold` (12 h); the `EF.Host` App Configuration refresher polls in the background because the Scheduler has no request middleware. Each multi-statement job step runs through `ITaskItemSystemRepository.ExecuteInTransactionAsync<T>` (EF.Data `ResilientTransaction`: execution strategy plus transaction), which refuses pending changes, clears the change tracker at the start of every attempt and returns the committed attempt's result; the handler adds that result to its count after the call returns. A retry after a lost commit re-runs the guards, upsert and staging against the rolled-back rows; a retry after a commit that landed is a no-op through the same guards (the overdue marks and the template advance return false, the stale tasks are gone) and reports 0, so the job's rows-affected undercounts that step rather than double counting. Saves inside keep `acceptAllChangesOnSuccess: true`: deferring `AcceptAllChanges` would leave the first attempt's rows tracked as Added, and the re-staged rows would collide with them. A job stages a deterministic id only for a row its own guarded write changed, never after a count-only guard: the overdue mark is one guarded `ExecuteUpdate` per task (a row another replica marked first returns false and is not announced again), and the recurrence inserts each occurrence with its own insert-if-absent upsert and announces and counts only the ones inserted (a pointer re-seeded over generated occurrences, as re-attaching a pattern does, re-walks rows that exist), and the stale cleanup deletes each task under its stale guard and queues blob-delete work, and deletes the attachment rows, only for the tasks that delete removed (two overlapping runs no longer both queue the same work ids, and a task reopened between scan and delete keeps its attachments). `RETURNING` would say which rows one statement changed, but it is not portable through `ExecuteUpdate` on both providers. | D-007, D-006, D-073 | confirmed | Exercises scheduler, the lane broker, and domain-service reuse. Seeding through `ICronTickerManager.AddAsync` before the host runs fails every call (TickerQ builds its function table in `RunAsync`), so no job ever ran; `SchedulerCronSeedingTests` proves seven rows after start and none added by a restart. Before the per-attempt clear, a commit retried after a transient failure threw "already being tracked" on the re-staged outbox or blob-delete row in all three jobs; `Test.Integration/SchedulerTransactionRetryTests.cs` injects one provider-transient exception before and after the commit on PostgreSQL and SQL Server. Staging every row of a tenant group after a non-zero mark count failed the run on `PK_OutboxMessage` when a competing replica had marked part of the page, so did staging every occurrence after a re-seeded pointer, and stale cleanup failed on `PK_BlobDeleteWork` when an overlapping run had removed part of the batch; the same class stages both on PostgreSQL and SQL Server. | Phase 5c |
| D-010 | Profile | Reference app scope | Full scaffold, comprehensive tests, optional hosts enabled | none | confirmed | Reference app must prove every major instruction pattern - once, not per entity. Deliberate per-entity asymmetry: `StructureValidator` on aggregate roots only (TaskItem, Category, Tag, Attachment), `CommandValidators` and a standalone updater on TaskItem only (sole aggregate with child collections), dedicated `RepositoryTrxn` on aggregate roots per GR-15; simple children (Comment, ChecklistItem) use generic repositories and inline updates. | All phases |
| D-011 | Local dependencies | Local boot strategy | Emulators where available; no-op/lazy-optional for deployment-only services | D-010 | confirmed | Scaffold must run locally without Azure provisioning. | Phase 3, Phase 5b, Phase 5e |
| D-012 | Relationships | Attachment ownership | Polymorphic `OwnerType` + `OwnerId`, no owner navigation collections | D-003, D-005 | confirmed | Avoids conflicting FK constraints for shared attachment ownership. | Phase 1, Phase 2, Phase 5a |
| D-015 | Orchestration | Workflow engine selection | `EF.FlowEngine` (SQL state store, outbox, circuit breaker, admin API, Blazor dashboard; version pinned in `Directory.Packages.props`) | D-003 | confirmed | Demonstrates durable AI-driven orchestration with human-in-loop, sagas, and atomic outbox. Reuses existing SQL Server + Azure OpenAI; no new infrastructure resource. Three workflows shipped: `ai-task-triage`, `ai-task-decomposer`, `compliance-check`, plus the `compliance-check-item` child workflow. Workflow nodes use only the registered `taskflow-api`, `integration-events` and `ai-agent` clients, and JSON seeding saves every definition through the engine's validating registry, which rejects an unregistered clientRef or an unknown node config key, so a bad definition stops host start: `FlowEngineClientRegistrationTests` resolves every shipped clientRef against the application registrations on both lanes (RabbitMQ and Service Bus) and shows an unregistered one is reported as `CLIENT_NOT_REGISTERED`, and `WorkflowDefinitionValidityTests` shows an unknown config key fails validation. An inline loop (`bodyEntryNodeId`) runs one node per iteration and writes the iteration keys into the instance context, so a multi-node per-item flow is a child workflow (`subWorkflowId`), each child its own instance with the item in `params.currentItem`. `compliance-check` searches one page (50) of the started tenant's tasks due before `dueBefore` through the public API (the search has no tag filter and filters status by equality only, so completed tasks are included) and starts one `compliance-check-item` per task, at most 5 in parallel; the child's evidence `document` node takes its Error edge because TaskFlow registers no `IDocumentStore`, and the decision's default edge also covers no finding. `AiWorkflowIntegrationTests.ComplianceCheck_ScansOnlyTheStartedTenant_AndRemindsTheTaskWithExpiringEvidence` runs both definitions end to end with a test document store. | Phase 5e+, Section 14 |

| D-019 | Security | Column-level encryption for sensitive properties | SQL Always Encrypted on `TaskItem.SecureDeterministic` (DETERMINISTIC) and `TaskItem.SecureRandom` (RANDOMIZED); CMK/CEK created in `InitialCreate` via `EF.Data.MigrationSupport`, CMK stored as an Azure Key Vault RSA key. Deterministic column shows equality querying; randomized shows non-queryable at-rest protection. | Phase 5a, `infra/`, AppHost |
| D-020 | Data | Relational database provider | Dual provider: SQL Server or PostgreSQL, `Database:Provider = SqlServer \| PostgreSql` selects the provider for all four contexts (Trxn, Query, FlowEngine, TickerQ) and the migrator; both first-class and CI-tested | D-003 | confirmed | Proves the scaffold is not SQL-Server-locked; PostgreSQL is a common customer-selected target. `databaseProviders: [SqlServer, PostgreSql]` added to `resource-implementation.yaml`. | Phase 1, Phase 5a, D-003 amended |
| D-021 | Data | Optimistic concurrency token | Provider-neutral app-managed `long Version` concurrency token (`IsConcurrencyToken()`, incremented in the base context `SaveChanges` for modified roots) replacing `rowversion` | D-020 | confirmed | Same ETag value on both providers; works on the InMemory provider so Test.Unit can cover 412 paths (`ETag: "<Version>"`, strong). Alternative rejected: provider-native `rowversion`/`xmin` (different types, untestable in-memory, opaque ETags). `EF.Domain.EntityBase<TId>.Version` is the token; `EF.Data.DbContextBase` sets it to 1 on insert, increments it for modified entries, and stamps `CreatedAtUtc`/`ModifiedAtUtc` (`ITimestampedEntity`) from its clock. | Phase 1, Phase 2, D-031, D-033 |
| D-022 | Data | Primary key shape | Tenant-first composite primary keys `(TenantId, Id)` on every tenant entity, composite FKs `(TenantId, ParentId)` to children | D-020, D-001 | confirmed | On SQL Server this is the clustered index (drops the separate `CIX_*` indexes); on Postgres it makes every table distributable by `TenantId` (Citus/Azure PostgreSQL elastic clusters require the distribution column in the PK and unique constraints) without a future rewrite. Global-admin cross-tenant queries still work (no partition pruning, acceptable for system jobs). | Phase 1, D-025 |
| D-023 | Security | Column-level encryption for sensitive properties | One application-layer AES-256-GCM value converter for BOTH providers on randomized columns; deterministic equality via an HMAC-SHA256 blind-index sibling column (`SecureDeterministicHash`, indexed), ciphertext stored randomized; both secure properties and the blind-index shadow column are marked `IsSensitive()`, which the `EF.Data` audit interceptor masks on insert and update payloads, so the audit trail never stores their plaintext; data-encryption key wrapped by an Azure Key Vault RSA key (RSA-OAEP), cached in memory, local dev uses a config-provided key | D-020, D-003 | confirmed | User preference: one common approach across both providers rather than a provider-specific mechanism. Domain byte budget stays 200 plaintext bytes; storage column is `varbinary(max)`/`bytea` (GCM overhead: nonce 12 + tag 16). Supersedes D-019 (kept as a documented SQL-Server-only alternative in tech-design with a code comment at the converter registration). Consequence: EF.Data core drops SqlClient/Always Encrypted dependencies. | Phase 1, Phase 5a, D-019 superseded |
| D-024 | Data | Temporal value normalization | All `DateTimeOffset` and `DateTime` values normalized to UTC by `EF.Data` `RegisterUtcTemporalConversions` on both providers (an `Unspecified` `DateTime` is taken as UTC); new scale columns are named `*Utc` | D-020 | confirmed | Npgsql `timestamptz` rejects non-zero offsets; one converter keeps both providers on a single code path. Client display converts. | Phase 1 |
| D-025 | Data | Migration baseline | Exactly one initial migration per (context x provider) = 6, in two migration assemblies (`TaskFlow.Infrastructure.Data.Migrations.SqlServer`, `...Migrations.PostgreSql`) selected via `MigrationsAssembly`: `InitialCreate` (TaskFlow), `InitialFlowEngine`, `InitialTickerQ`. The rule is permanent: TaskFlow is the foundation new apps start from, so it never carries migration history, and a schema change regenerates the context's initial migration (delete it with its Designer file and snapshot, then `dotnet ef migrations add` it again per provider) instead of adding one. `Test.Architecture/MigrationBaselineArchitectureTests` fails when any context and provider pair has more than one migration, and `has-pending-model-changes` stays clean for all six pairs. A regeneration invalidates an existing database's migration history, so a local dev volume (`taskflow-postgres-data`, `taskflow-sql-data`) is dropped and recreated rather than upgraded (README). | D-020, D-022 | confirmed | A baseline with history would hand every new app the upgrade path of a schema it never had; data backfills and type conversions exist only to move an existing database, and a fresh baseline has none. The 2026-10-01 regeneration folded eight PostgreSQL and six SQL Server TaskFlow migrations (read model and audit, embeddings, jsonb, two-state inbox, audit start time, package inbox and outbox) and the D-074 idempotency-key table into `InitialCreate`, and removed the tests that proved the folded backfills. `migrationLifecycle` in `resource-implementation.yaml`; `TaskFlowMigrationHistoryCompatibility.cs` deleted. | Phase 1, 2026-10-01 |
| D-026 | Messaging | Transactional outbox ownership | TaskFlow's own transactional outbox + work tables (not FlowEngine's), built on `EF.Data.Outbox`: `OutboxMessage` and `BlobDeleteWork` (`LeasedWorkItem`) map into the TaskFlow write context (`ApplyOutboxModel`), `AddOutbox<TaskFlowDbContextTrxn>` stages domain events through `TaskFlowOutboxEventMapper` (envelope plus a `TenantId` header), and the Scheduler runs `AddOutboxDispatcher` over the lane's `IOutboxTransport`; the claim is provider-neutral EF Core (select candidate Ids, conditional lease-claim update, then read owned rows) | none | confirmed | A racing replica simply claims fewer rows. Single-statement provider-specific upgrade paths (SQL Server `UPDATE TOP...OUTPUT`, Postgres `FOR UPDATE SKIP LOCKED`) are documented only as code comments. Payload is a JSON string column via EF (`jsonb`/`nvarchar(max)`). Scheduler host drains both replicas, lease-based, adaptive poll. Claims skip rows at the configured `MaxAttempts` and dead-letter exhausted rows whose lease expired; transports return one result per message and each row settles on its own result on a bounded token that shutdown does not cancel, so one bad message never fails its destination group and a send the broker accepted is not re-published after a shutdown. | Phase 3, D-029 |
| D-027 | Data | Read routing | The Query context keeps its own connection string on both providers; SQL Server appends `ApplicationIntent=ReadOnly` (Hyperscale HA secondary), Postgres points at the Flexible Server read-replica endpoint | D-020 | confirmed | Reads that follow a write in the same request use the Trxn context (read-your-writes rule); replica lag is otherwise acceptable for read-model queries. | Phase 1, Phase 5a |
| D-028 | Data | Provider-neutral upsert | `EF.Data` `IRepositoryBase.UpsertAsync`/`UpsertRangeAsync(entity, match, whenMatched)` (FlexLabs.EntityFrameworkCore.Upsert under the hood: `MERGE` on SQL Server, `ON CONFLICT` on Postgres) for idempotent create-if-absent | D-026 | confirmed | Avoids hand-written provider-specific upsert SQL for outbox rows and recurrence occurrences. The package owns the FlexLabs dependency, so no repository takes it directly; a null `whenMatched` is DO NOTHING (inbox claim, occurrences, audit append) and an explicit one replaces every non-key column (read-model and embedding upserts). | Phase 1, Phase 3 |
| D-029 | Messaging | Consumer idempotency | Two-state inbox `ConsumerInbox (Consumer, MessageId, ClaimToken, ClaimedAtUtc, LeaseExpiresUtc, CompletedAtUtc)`, PK `(Consumer, MessageId)`. A delivery claims with a 60 s lease that it renews every 20 s while the handler runs, completes after the work, and releases on failure (token-guarded). A redelivery that finds a live claim polls it (`WaitPollInterval` 1 s, bound lease + 5 s): completed means ack as a duplicate, expired means take over, still live returns `ConsumeDisposition.InProgress`, which the transport retries. The consumers derive from `EF.Messaging` `IntegrationEventConsumerBase` over the `EF.Data.Outbox` `InboxStore<TaskFlowDbContextTrxn>` on the same `ConsumerInbox` table (`Consumer` up to 128 characters). A holder stops renewing after `MaxClaimDuration` (package default 10 min, kept: every TaskFlow consumer handler finishes well inside it), so a hung handler's claim lapses and a redelivery takes over. Timings bind from `Messaging:Inbox`; completed and abandoned rows are hard-deleted by retention. | D-020 | confirmed | A claim committed before the work loses the effect on a crash or a concurrent redelivery. The bounded wait exists because RabbitMQ (the default broker) requeues a retry immediately, which would dead-letter the message after a consumer crash while the dead holder's lease is still live. Provider-neutral; FlowEngine `StartRequest.IdempotencyKey` is set as well. | Phase 3, D-026 |
| D-030 | Data | Provider-branch discipline | Provider branches exist only where EF Core forces them (`UseSqlServer`/`UseNpgsql`, per-provider migration assemblies, the PostgreSQL-only column types in `TaskFlowDbContextBase.ConfigurePostgreSqlModel` (`jsonb`, `vector`), the SQL Server binary collation on the D-074 key columns in `IdempotencyKeyConfiguration`, Npgsql UTC requirement); model-wide conventions (`HavePrecision(18, 4)`, UTC converters) are provider-neutral in `ConfigureConventions`; everything else is one code path with a comment naming the provider-specific customization | D-020 | confirmed | Keeps the dual-provider surface maintainable; prevents provider-branch sprawl in `OnModelCreating`. | Phase 1 |
| D-031 | Data | Concurrency scope | Aggregate-level ETag: root `TaskItem.Version` is the ETag; child mutation methods call a private `MarkAggregateChanged()` that touches `ModifiedAtUtc` so the root is marked Modified and its `Version` bumps; child PUT/DELETE use the root ETag | D-021 | confirmed | One concurrency currency per aggregate avoids per-child ETag bookkeeping. Child DTOs still expose their own `Version` for display, not as If-Match currency. | Phase 2, D-032 |
| D-032 | Data | Concurrency conflict status code | 412 (not 409) for stale writes: `EF.Data.Contracts.ConcurrencyGuard.Require` and every `OptimisticConcurrencyWinner.Throw` save raise `PreconditionFailedException`, which the `EF.AspNetCore.Concurrency` If-Match filter answers with 412 and the current ETag; a policy-free save's `DbUpdateConcurrencyException` is classified 412 as well; 428 when `If-Match` is missing (`RequireIfMatch()`); `If-Match: *` is the explicit trusted-automation override, sent by each FlowEngine PATCH node's own `"headers"` config (`EF.FlowEngine.Definition.NodeConfigs.IntegrationNodeConfig.Headers`, forwarded by `IntegrationNodeExecutor`); a `*` write states no precondition, so it never answers 412: it reaches the write as `expectedVersion == null`, the guard passes, and the read, apply and save run inside the D-073 fresh-read retry, so a write that lands between the read and the save makes it re-read and apply again, and a race lost on every attempt is 409. A `*` PUT is a full replacement of the aggregate as re-read, so a child added concurrently and not in the payload is deleted with the replace; a `*` PATCH changes only the fields it carries. The node `retryPolicy` is the only retry owner (the `taskflow-api` client sends once per node attempt, D-063), and every `taskflow-api` node, loop-body nodes included, declares one (3 attempts, exponential backoff), so a `*` PATCH is resent on 409, 429 and 503 (the engine's unsafe-method default) and never on 412: the engine treats 412 as permanent, and its definition validator refuses 412 in any retry list | D-031 | confirmed | 412 Precondition Failed is the correct HTTP semantics for a stale If-Match. A wildcard caller named no version, so a 412 would report a precondition it never sent. The FlowEngine override is node config, so no app-side transport handler exists. Resending a stale If-Match unchanged cannot succeed, while 409/429/503 on a `*` write are transient. `WorkflowDefinitionValidityTests` pins each node's policy and the absence of 412; `FlowEngineWorkflowTests` shows a 503 PATCH resent once and a 412 PATCH sent once. The 412 carries the current ETag only from the If-Match filter (`PreconditionFailedException.Current`): `ExceptionHandlerMiddleware` clears response headers, so a 412 raised outside the filter has none. | Phase 2, handler mitigation superseded |
| D-033 | Data | Idempotent create record | No response-replay table: an optional caller-supplied UUIDv7 id, the entity row itself is the idempotency record; equivalent replay returns 200 + existing entity + ETag, divergent payload is a 409 (`EF.Common.Contracts.ConflictException`) | D-021 | confirmed | Avoids a second source of truth for create idempotency.
