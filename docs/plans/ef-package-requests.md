REQUIRED: EF.FlowEngine / Clients.Http: confirmed against decompiled 1.0.163 (`dotnet ilspycmd`). `BuildHeaders` is real and used, but only by `FetchNodeExecutor` via `FetchNodeConfig.Headers` (`Dictionary<string,string>?`, "fetch" node type - raw HTTP, optional `ClientRef`). `IntegrationNodeConfig` (the "integration" node type `ai-task-triage.json`'s PATCH nodes use, calling a registered `IRequestResponseClient`) has **no** `Headers` property, and `IntegrationNodeExecutor.ExecuteAsync` never sets `ClientRequest.Headers` - it only sets `Method`, `Url`, `Body`, `IdempotencyKey`. 29. REQUIRED: EF.Grpc findings, confirmed by decompiling `EF.Grpc` 1.0.68 (no newer version published; also ships no XML docs - add them):
    - `ServiceErrorInterceptor.UnaryServerHandler` hardcodes `StatusCode val = (StatusCode)13;` (`Internal`) for every caught exception with no way to map an application exception type to a different gRPC status (e.g. `NotFound`, `InvalidArgument`, `PermissionDenied`); TaskFlow's own `TaskFlowReadGrpcService` does its own per-exception-type `RpcException` mapping instead of using this interceptor for that purpose (G3). Acceptance: a pluggable `Func<Exception, StatusCode>` (or an `IGrpcErrorStatusMapper` seam) on `ErrorInterceptorSettings`, defaulting to today's blanket `Internal`.
    - The leak is worse than "opt-in": `ErrorInterceptorSettings.IncludeLogDataInResponse` defaults to **`true`**, and even when set to `false` the raw `ex.Message` is still sent to every caller regardless, because it is baked into `new Status(val, ex.Message)` - the `Status.Detail`, which becomes the wire-visible `grpc-message` trailer - not only into the extra `"Exception"` trailer the flag gates. Acceptance: default `IncludeLogDataInResponse` to `false`, and stop passing `ex.Message` as the `Status` detail by default (a generic "Internal error" detail, with `ex.Message` available only through the gated extra trailer or server-side logs).
    - `AddGrpcClient2` always builds (or accepts only) an `HttpClientHandler` (`new HttpClientHandler()` when `primaryHttpMessageHandler` is null), so a caller cannot supply a `SocketsHttpHandler` (recommended for HTTP/2 connection reuse) or a bare test `HttpMessageHandler` fake. Acceptance: accept `HttpMessageHandler` (or a `Func<HttpMessageHandler>` factory) and only apply the `HttpClientHandler`-specific options (`MaxConnectionsPerServer`, `ClientCertificates`) when the supplied/created handler actually is one.
    **Not used**: TaskFlow's `TaskFlowReadGrpcService` (G3, D-054) uses plain `Grpc.AspNetCore`/`Grpc.Net.ClientFactory` directly rather than `EF.Grpc`, specifically because of these three gaps.
