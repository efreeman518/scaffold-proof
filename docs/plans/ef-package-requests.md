REQUIRED: EF.FlowEngine / Clients.Http: confirmed against decompiled 1.0.163 (`dotnet ilspycmd`). `BuildHeaders` is real and used, but only by `FetchNodeExecutor` via `FetchNodeConfig.Headers` (`Dictionary<string,string>?`, "fetch" node type - raw HTTP, optional `ClientRef`). `IntegrationNodeConfig` (the "integration" node type `ai-task-triage.json`'s PATCH nodes use, calling a registered `IRequestResponseClient`) has **no** `Headers` property, and `IntegrationNodeExecutor.ExecuteAsync` never sets `ClientRequest.Headers` - it only sets `Method`, `Url`, `Body`, `IdempotencyKey`. A `"headers"` key added to an integration node's `config` is silently ignored (`ExecutorJsonOptions.NodeConfig` has no `UnmappedMemberHandling.Disallow`), not an error - a real, load-bearing gap, not a documentation gap. Acceptance: `IntegrationNodeConfig` gains `Headers { get; init; }` and `IntegrationNodeExecutor` forwards it into `ClientRequest.Headers` the same way `FetchNodeExecutor` does. `ai-task-triage.json`'s PATCH nodes already carry `"headers": { "If-Match": "*" }` (harmless no-op today) so the fix goes live the moment this ships - no workflow JSON change needed. Confirmed again 2026-09-04 directly against the installed `EF.FlowEngine` 1.0.163 package XML docs (`ef.flowengine/1.0.163/lib/net10.0/EF.FlowEngine.xml`): `IntegrationNodeConfig` documents `ClientRef, Integration, Method, Path, Body, Request, ResponseMapping, IdempotencyKey` and no `Headers`, while `FetchNodeConfig` does document `Headers`. `tests/Test.Integration.FlowEngine/WorkflowDefinitionValidityTests.cs:147` (`IntegrationNodeConfig_HasNoHeadersProperty_PackageRequest18`) reflects `GetProperty("Headers")` and asserts null specifically so this request's resolution trips a build failure automatically the day the package adds it - remove the app-side mitigation (`FlowEngineIfMatchOverrideHandler`, D-032) at that point. `TriageWorkflow_AppliesSuggestedPriority_ThroughRealApi` (Test.Integration) is green today only because of that mitigation, not because this gap is closed.

Re-verified against decompiled 1.0.163: no such function exists (searched the whole assembly for `newGuid`/`uuid`/`CreateVersion7`/`CreateVersion5` - only internal `Guid.NewGuid()` calls unrelated to workflow expressions), and `LoopNodeConfig` exposes no per-iteration id field (`ItemAs`/`IndexAs` only). `ai-task-decomposer.json`'s `n-loop-create-one` still has no way to mint a stable `Id` for its `POST /api/v1/task-items` body, so the loop stays non-idempotent on retry - `idempotencyKey` (a plain string like `"{taskId}-subtask-{currentIndex}"`) only feeds the client's own retry dedup, not the API's UUIDv7 body `Id`.
